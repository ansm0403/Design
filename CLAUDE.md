## Prerequisite

When performing real project work — creating or changing designs, implementing Steps,
or updating docs — begin the response with "지침에 의거하여 답변할게" to signal that this
file is being applied. Skip it for pure concept questions or casual chat where these
guidelines do not apply.

## Project

A **design system monorepo** — design tokens + a reusable UI component library.
Built for learning, but targets production-grade code quality. Focused on the most
commonly used core components, not an exhaustive component set.

Two packages, strictly layered:
- `@my-ds/tokens` — design values as CSS variables (no React, no runtime deps)
- `@my-ds/ui` — React component library that consumes the tokens

## User Context

- **Experienced**: React, TypeScript, state management, frontend development
- **New to**: design systems, monorepos, pnpm workspaces, Tailwind v4 (CSS-first),
  tsdown, Storybook, library publishing
- When explaining any topic listed under "New to", give beginner-friendly explanations
  and add short inline code comments for non-obvious concepts (peerDependency,
  `sideEffects`, `workspace:*`, polymorphic components, `forwardRef`, headless pattern).
- The user follows the Steps as a learning exercise. Implementing several related
  Steps in one batch is the norm (see Workflow Rules) — just don't push past the
  agreed scope or skip the user's confirmation. Apply the same engineering standards
  throughout — proper typing, accessibility, build correctness — but avoid
  over-engineering (no speculative abstraction, no premature generalization).

- Tier-3 components (Accordion, Select, Grid, List).

## Immutable Rules

These must never be broken. If a request conflicts with one, propose an alternative.

1. **Dependency is one-directional**: `tokens → ui`. `tokens` must NEVER import `ui`
   (circular dependency = build hell).
2. `@my-ds/tokens` has **zero runtime dependencies** — it does not even know React.
   It is pure values + generated CSS.
3. All design values (color, spacing, typography) are defined as tokens ONLY.
   Never hardcode colors/spacing/fonts inside components.
4. CSS variables are generated by `generate-css` ONLY. Never hand-write CSS variable
   files — the token Object is the single source of truth; CSS is a derived artifact.
5. `react` / `react-dom` are **peerDependencies** of `@my-ds/ui`, never `dependencies`
   (a bundled React causes duplicate-React "Invalid hook call" errors in consumers).
6. Tailwind v4 stays **CSS-first**. Do NOT create `tailwind.config.js` or preset files.
   The token↔Tailwind bridge lives in `packages/ui/src/theme.css` via `@theme`.
7. Semantic tokens are exposed under a **single key** (`primary`, `danger`, …).
   Components must NOT be aware of light/dark — only the CSS variable value switches.
8. Do NOT expand the MVP scope (Phases 0–5, Tier-1/2 components) without user approval.

## Workflow Rules

- **The default execution mode is multi-Step (batch).** Group related Steps and
  implement them together in a single pass — this is the norm, chosen to save time
  and tokens.
- Drop to one-Step-at-a-time execution ONLY when a Step is genuinely large, risky,
  complex, or touches a critical part of the project. Single-Step is the exception,
  not the default.
- Before execution, state which mode applies. Batch is assumed and needs no
  justification; when choosing single-Step, give a one-line reason for the exception.
- After completing a batch of Steps (or an isolated single Step), stop, summarize
  what was done, and wait for user confirmation before continuing.
- Batch freely within a single Phase. Do NOT combine multiple Phases in one batch
  unless their combined scope is small, low-risk, and clearly manageable.
- Before any multi-file or architectural change, propose a short plan and wait for approval.
- If a design decision changes, edit `architecture.md` FIRST, then change the code.
- On Step (or batch) completion: run the `edgecase-review` skill first. If WARN/FAIL items are found, document them in `docs/edgecase/phase-{N}.md`. Then check the item in `mvp-checklist.md` and add a work-log entry.
- Record pitfalls / know-how discovered during a Step as a comment in the matching
  Step of `phases.md`.
- Every package's `package.json` must declare `"sideEffects": ["*.css"]`, and CSS must
  be exposed via the `exports` field — never rely on auto-injection.
- Need a package script? Inspect `package.json` instead of guessing the command.
- Before installing a new library, verify the latest stable version and its
  compatibility with the existing stack.
- Avoid editing unrelated files. Stay within the scope of the current Step.
- Uncertain about a version/config? Do NOT assert — verify first. If blocked, present
  options and ask the user rather than proceeding arbitrarily.

## Error & Edge Case Defaults

- The `exports` paths in `package.json` MUST match the actual `dist` output. Verify
  by running the `build` script and inspecting `dist`, not by assuming.
- Components must NOT crash on invalid or missing props — fall back to sane defaults.
- Every interactive component ships keyboard operability and ARIA attributes by default.
- Build artifacts (`dist/`) are gitignored. Verification is done via build-command output.

## Testing Policy

- Tools: **Vitest 3 + @testing-library/react + vitest-axe**. Environment is **jsdom**
  (happy-dom is incompatible with axe-core).
- Introduced in Phase 4. No tests before then.
- Test **behavior**, not implementation details: clicks, `onChange`, state transitions,
  and accessibility (`vitest-axe` → `toHaveNoViolations`).
- Prefer user-facing queries: `getByRole`, `getByLabelText`.
- Test files live next to the component: `Button.tsx` → `Button.test.tsx`.
- Per-Step test scope: see Phase 4 in `phases.md`.

## Commit Convention

Use conventional commits: `feat:`, `fix:`, `refactor:`, `docs:`, `chore:`, `test:`.
Keep each commit scoped to a single Step when possible.
